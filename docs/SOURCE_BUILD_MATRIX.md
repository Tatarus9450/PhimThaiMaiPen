# Source-build feasibility and dependency inventory

**Delivery scope changed on 2026-09-12:** native application plus GitHub publication only. Source-only Flatpak/Flathub work is paused. Partial Torch compilation is cached, not completed. Historical inventories and source proofs below remain research evidence, not release requirements for this delivery

Evidence snapshot: 2026-09-12, x86_64, installed experimental Flatpak `io.github.tatarus9450.PhimThaiMaiPen`. This document inventories the **64 distributions under /app** before the proposed Librosa removal; SDK Python distributions were excluded by installation path. Host-managed FastFlowLM/AMD runtime binaries and model weights are outside this Python inventory and need their own distribution evidence. It is a packaging work plan, not a claim that the installed wheels were compiled from source.

All **55 published sdists** in the inventory were downloaded into memory and SHA-256 checked against their exact-version PyPI JSON records. Their top-level build metadata was inspected. Eight distributions have **no PyPI sdist** at these versions; five pinned Git trees below cover them because all four Qt distributions share a source tree. The remaining distribution is this local application. Source availability and a verified archive hash do not prove a successful offline build.

[Flathub requirements](https://docs.flathub.org/docs/for-app-authors/requirements) require source-available applications and dependencies to be built from source. An existing application's binary packaging pattern is evidence of its implementation, not blanket permission for this application to ship the same binaries.

## Implementable route

1. Freeze the complete runtime graph and the separate build-tool graph. The inspected root file pins most roots but leaves `protobuf` and transitive packages floating; the observed versions below include protobuf 7.36.1, SciPy 1.18.1 and scikit-learn 1.9.1. Do not regenerate from today's unconstrained latest releases during an offline build.
2. Apply and test the small Qwen optional-import changes below, then resolve an ASR-only graph. This removes **20 of the 64 distributions**, including the LLVM 22/Numba/SciPy branch. Keep source pins for the old graph here as migration evidence.
3. Build Shiboken/PySide from its source tree against SDK Qt, with only required modules; build pure Python packages, C extensions and Rust extensions from the pinned sdists. Use SDK libffi/libsndfile rather than bundled wheel libraries.
4. Build CPU PyTorch from the pinned recursive Git source. Choose a source-built BLAS implementation and retain tested CPU kernels. Test actual Qwen model loading, generation, cancellation and both languages in this image.
5. Build OpenVINO, OpenVINO Tokenizers and GenAI using the same SDK/compiler and compatible pins. Supply oneTBB and all fetched C++ sources before entering the offline build. Start with CPU plus the IR frontend; add GPU/NPU through separate verified configurations.
6. Generate the final source-only manifest and offline cache; run a clean build with networking unavailable during compilation, app smoke/audio/portal tests, dependency/license checks, Flatpak/AppStream lint and external Flathub review. Only accepted publication establishes availability in Discover with Flathub enabled.

The existing local wheel artifact remains useful for integration testing. A binary `extra-data` add-on is a possible proposal for reviewers, **not an approved exception**. The [SpeechNote CPU module](https://github.com/flathub/net.mkiol.SpeechNote/blob/77a7b501fffa9cf672971574a718177a21ca7cd4/python3-modules-x86-64.yaml#L50) uses binary Torch wheels, while its [AMD beta add-on](https://github.com/flathub/net.mkiol.SpeechNote.Addon.amd/blob/beta/net.mkiol.SpeechNote.Addon.amd.yaml) extracts downloaded binary packages at installation. Neither is a reusable Torch source-build recipe.

## Qwen dependency reduction: observed proof

Qwen-ASR 0.0.6 imports Librosa eagerly in `qwen_asr/inference/utils.py:23`, but this file only uses it for a string-path decoder at line 146 and non-16-kHz resampling at line 199. Its NumPy tuple path and mono conversion do not require Librosa. [Upstream file](https://github.com/QwenLM/Qwen3-ASR/blob/main/qwen_asr/inference/utils.py); line numbers refer to the hash-verified 0.0.6 sdist below.

Minimal patch candidate, preserving those optional operations:

```diff
-import librosa
 ...
     else:
+        import librosa
         audio, sr = librosa.load(x, sr=None, mono=False)
 ...
     if sr != SAMPLE_RATE:
+        import librosa
         audio = librosa.resample(audio, orig_sr=sr, target_sr=SAMPLE_RATE).astype(np.float32)
```

Also retain the existing Nagisa patch: move its top-level import in `qwen3_forced_aligner.py` into `Qwen3ForceAlignProcessor.tokenize_japanese`, immediately before `nagisa.tagging`. Keep the app's contract: FFmpeg converts all audio to mono 16 kHz, including warm-up; Qwen receives NumPy tuples. Do not expose the optional uninstalled decoder/resampler/forced-aligner operations as supported app features.

A read-only experiment ran inside the installed Flatpak using CPython 3.13 and CPU Torch 2.11.0+cpu, four Torch threads and the cached Qwen 0.6B checkpoint. It patched only the imported source in memory. A custom import finder rejected actual imports of Librosa, Numba, llvmlite, SciPy, scikit-learn, soxr, Nagisa, DyNet, Gradio, Flask and the other unused demo/aligner modules; availability probes were made to behave as if those packages were absent. **Both real-audio transcriptions passed and no blocked package was loaded.**
